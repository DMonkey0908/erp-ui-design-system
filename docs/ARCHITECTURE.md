# Architecture

Why the repo is shaped the way it is, and which decisions are still open.

## The problem this shape solves

A UI design ecosystem covering several domains — operational tools, consumer
web, mobile, commerce, system utilities — has an obvious naive structure: one
self-contained spec per domain, shipped in each assistant's format.

That structure fails predictably. Eight domains times three assistant formats is
twenty-four documents. Most of their content is identical, because "focus must
be visible" and "numbers need tabular figures" do not vary by domain. Within a
few months they disagree, and the disagreement is **silent** — an assistant
quotes whichever file it loaded, and nobody finds out until a reviewer notices
two projects built from the same repo following different rules.

So: **author once, generate the rest.**

```
core/          rules true for every interface        ─┐
packs/<id>/    what one domain decided                ├─→ tools/build.mjs ─→ dist/
                                                      ─┘
```

## Core and overlay

**Core** holds method, never values. "An accent needs one value per surface" is
core. `#b3121b` is not — the moment core contains a hex it has picked a domain's
side. The build enforces this: a concrete colour outside a code block in
`core/references/` fails the build.

**A pack** holds what its domain decided, and *never repeats a core rule*. Where
a pack needs to reference one it points at it (`see core/03-layout.md`) and adds
only the domain-specific consequence.

That "never repeats" rule is the one that does the work. It is also the one
under constant pressure, because repeating a rule always feels helpful in the
moment. The test: if another domain could reasonably choose differently, it
belongs in the pack; if it would be wrong everywhere, it belongs in core.

**Overrides** are legal. A pack may contradict a core rule if it declares the
override in `pack.json` and defends it in `PACK.md`. What is not legal is
contradicting core silently. Two exceptions cannot be overridden at all — the
accessibility minimums and the chart honesty rules — because their cost lands on
someone who is not in the room when the decision is made.

## The surface-role vocabulary

Packs describe their palette in shared roles — chrome, canvas, content,
floating, accent, semantic — so two packs can be compared and a reader can move
between them. The ERP pack makes chrome dark and content light; a consumer-web
pack may make both light. The roles are what let core talk about surfaces at all
without picking a look.

## Generated output

`dist/` is committed. Most users copy a file out of it and never run Node, so
the repo has to work as a download. The cost is that `dist/` can go stale
against its sources, which is what `node tools/build.mjs --check` exists for —
CI runs it, and a pull request that edits a source without rebuilding fails.

Three output shapes, because the three assistants load context differently:

| Output | Shape | Why |
|---|---|---|
| `dist/claude/<skill>/` | `SKILL.md` + `core/` + `pack/` + `assets/` | Claude loads `SKILL.md` first and pulls a reference only when the task needs it. Progressive disclosure means the references can afford depth. |
| `dist/gemini/<id>.GEMINI.md` | One merged file | Gemini reads a single context file. |
| `dist/gpt/<id>.AGENTS.md` | One merged file | Codex, Cursor and friends read `AGENTS.md`. |
| `dist/gpt/<id>.custom-gpt-instructions.md` | Hand-written, copied | The Instructions field is capped at 8000 characters, so it cannot be generated by concatenation. The build verifies the limit. |

The merge demotes every heading one level so several documents sit under one H1,
and it skips fenced code blocks while doing so — a `# install` comment inside a
bash block is not a heading, and demoting it corrupts the snippet.

## Open decisions

These are deliberately unresolved. They are the first things worth arguing
about.

### 1. The merged files are large

Adding core pushed `erp.GEMINI.md` from ~20KB to ~80KB, roughly 20k tokens, and
a `GEMINI.md` or `AGENTS.md` is in context on **every** request. Claude's build
is unaffected, because it only loads the reference it needs.

That is a real regression for Gemini and Codex users, and it gets worse as core
grows. Options:

- **Accept it.** Modern context windows absorb it; the cost is tokens, not
  correctness.
- **Generate a condensed merge.** Mark sections as essential vs. elaboration in
  the source, and merge only the essential ones. Costs the reasoning, which is
  the part that makes these rules stick.
- **Ship the rules and link the reasoning.** A compact merged file that points
  at the repo for the "why". Works only for readers who will follow a link, and
  an assistant will not.
- **Per-pack choice** via a `mergedProfile` field, so a dense pack can be terse
  and a subtle one can be complete.

No option is obviously right, which is why it is not decided.

### 2. How packs relate to each other

Right now packs are independent overlays on core. Real products are not: an
e-commerce admin is a back-office tool with a commerce vocabulary, and a SaaS
dashboard sits between an ERP and a consumer app.

Should a pack be able to extend another pack, rather than only core? It is more
expressive, and it is also how a two-level system turns into a dependency graph
nobody can hold in their head. Worth resisting until a second pack actually
demands it.

### 3. Where component specs live

Components are currently per-pack, on the argument that a card in a back-office
tool and a card in a shopping app share a name and nothing else. That is true of
cards. It is less true of a table, a form field, or a dialog, where the
structural advice really is universal and only the density differs.

There may be a middle layer: universal component *structure* in core, with
per-pack values. Or that may be over-engineering. Waiting for the second pack to
tell us.

### 4. Nothing is tested against a real build

Every rule here was extracted from shipping code, but the **packaging** has not
been proven: nobody has yet installed the generated skill and built a screen
from it end to end. Until that happens, treat the ergonomics — not the content —
as unverified.

## Adding a pack

See `AUTHORING.md`. The short version: copy `packs/_template/`, write a thesis
another domain would argue with, fill in the values, run the build.
